What training data and objectives change at Top-3 and Top-5

What the experiments found

Two findings stand out in this empirical survey. Grouped binary cross-entropy and listwise cross-entropy plus binary cross-entropy both improved complete recovery over an existing pointwise checkpoint. Their Complete@5 scores differed by just 0.17 percentage points. In a separate comparison using the same composite loss, the checkpoint trained on more and broader data reached 74.94% Complete@3 and 80.10% Complete@5, up 9.04 and 5.94 points over its predecessor on the same test queries. Recall improved for items with positives in the earlier training set and for items that gained positives in the expanded set. The expanded fit also took more optimizer updates, so the gain reflects the training changes taken together.

Why complete recovery matters

The task is to rank relevant items from an internal enterprise catalog given a short text query. Catalog details are withheld. A reviewer uses the shortlist to decide which items to inspect first. Each item has a profile with a name, a description and other attributes. A query can have several correct answers. Labels are mapped to canonical item identities so that different names for the same item count once.

Consider a query with three relevant items, A, B and C. A Top-3 list of A, X and B puts a relevant item first and recovers two thirds of the set. A reader working from that shortlist still misses C. Complete@3 asks whether the first three suggestions cover the query. Complete@5 tests what two more suggestions buy. We use these depths to compare a quick first pass with a slightly longer review. Macro Recall measures partial recovery, and Hit@1 describes the first result.

Three design choices that often get mixed up

When someone calls a model “listwise,” they may mean the input it reads, the loss it learns from, or the order it emits. Those are three different design choices. The easiest way to separate them is to follow one score from query text to the final shortlist.

From cross-encoders to candidate-aware rerankers

A cross-encoder reads the query and candidate together. In Passage Re-ranking with BERT, a classifier turns the combined representation into a relevance score. MonoT5 takes the same broad approach with a text-to-text model and reads a true or false answer. Qwen3-Reranker uses a decoder and a yes/no readout. The models differ in architecture and scoring head, but each can score candidates independently and sort the scores afterward.[4] [5] [2] [6]

There are also designs where candidates interact during inference. Pairwise Ranking Prompting asks an LLM which of two candidates should rank higher. RankGPT generates an ordering from a list prompt. The compact jina-reranker-v3 reads candidates in the same context so their representations can interact before scoring. These approaches change what the model can observe when it makes a decision. A loss that compares independently produced Qwen scores during training leaves that inference interface unchanged.[7] [8] [9]

Pointwise, pairwise and listwise on the same example

Pointwise, pairwise and listwise objectives differ in the supervision they apply to the same candidates.[1]

Pointwise

A = relevant; X = irrelevant

Binary cross-entropy penalizes errors on each relevance label. Grouped binary cross-entropy organizes examples by query and still applies a binary target to each candidate.

Pairwise

A should rank above X

A preference loss penalizes an insufficient score gap between sampled positives and negatives. The training signal depends on which pairs the sampler supplies.

Listwise

Score A against the candidate group

Cross-entropy over a group rewards a higher relative score for the target positive. In the expanded fit, each group contains one positive and 15 negatives.

The composite objective combines listwise cross-entropy with binary cross-entropy. The listwise term compares scores inside each training group, while binary cross-entropy supplies per-candidate relevance supervision. Queries can have several correct items in evaluation. A group with one target positive cannot directly optimize whether all of them appear in the final Top-3.

At inference, each evaluated Qwen3-Reranker-0.6B checkpoint scores one query–candidate pair at a time using the difference between its yes and no logits.[2] The listwise training signal therefore operates over a group of independently computed scores. Pairwise learning provides a useful methodological comparison here. The Qwen comparisons have no matched pairwise-trained arm. A separate Laya pilot below tests a pairwise term.

What each loss actually pushes up or down

Pointwise. With score s and binary label y, BCE applies −y log σ(s) − (1−y) log(1−σ(s)) to a candidate. Correctly raising the score of C helps even if B still loses to a distractor. Grouped BCE keeps examples from the same query together, which changes the supervision the sampler supplies, while the loss still sees individual binary labels.

Pairwise. RankNet is a classic example. The loss for a relevant candidate B and an irrelevant candidate X can be written as −log σ(sB − sX). The same example updates both sides of the preference. Which negatives you sample matters: an easy negative that already scores well below B teaches less about a shortlist decision than X just above it. LambdaRank-style methods connect gradient weights to the impact of swaps on a ranking metric. Neither construction automatically optimizes full set recovery at a particular K.[10] [11]

Listwise. A group softmax makes the candidates compete for probability mass. For one target positive C, the loss is −log softmax(s)C. ListNet compares score-induced and label-induced list distributions. ListMLE instead assigns likelihood to an ordered list. Our composite recipe uses the single-target group cross-entropy plus a binary term. The group identifies a target positive at training time. A query with several relevant items in evaluation still asks the model to place the full set near the top.[1] [12]

Reward-based reranking is a further option. Rank-R1 uses reinforcement learning to teach a reranker to reason over candidates. A reward built around Complete@3 would bring training closer to the metric, but it would be sparse when one missing candidate makes the whole set incomplete. This survey’s measured recipes use supervised learning.[13]

    How we compared the models

    Each reranker starts with a frozen pool of up to 100 candidate items. Both main comparisons used lexical retrieval based on BM25F. Metadata supplied with each query narrowed which items were eligible before retrieval. The eligibility filter did not receive the relevance labels. Historical results below distinguish unrestricted catalog pools from metadata-filtered pools. Models within each comparison see the same candidates. We deduplicate by canonical item identity and retain relevant items missed by retrieval in the metric denominator.

    Training recipe comparison. Table 1 uses 594 queries, including 97 with multiple relevant items. Its query format allowed a summary, a description and an optional auxiliary analysis field. The pool contains 714 of 753 gold labels (94.82%). Fifteen queries have more than three gold items, and four have more than five. The pointwise checkpoint was rescored using the same inputs as the grouped BCE and Listwise + BCE checkpoints. The original training-to-evaluation audit reported no exact query-identity overlap or near-duplicate links at its tested threshold.

    Expanded training comparison. Table 2 uses 387 queries from the frozen test split, including 87 with multiple relevant items. Both checkpoints are evaluated on summary and description only. The pool contains 505 of 540 gold labels (93.52%). Seventeen queries have more than three gold items, and five have more than five. The common unseen filter excludes query groups used to fit either checkpoint or the historical fusion comparator, a ranking method that mixes a neural score with additional features. Both its neural fit and the fit of its feature weights are covered by the filter. The researchers had already inspected both evaluation cohorts.

    The earlier checkpoint in Table 2 is the Listwise + BCE checkpoint in Table 1. Both use listwise cross-entropy + 0.25 × grouped binary cross-entropy. The expanded Qwen3-Reranker-0.6B checkpoint starts from the original base and uses LoRA for two epochs on the training split of a frozen 60/20/20 dataset.[3] The earlier fit took 758 optimizer updates and the expanded fit took 2,046. On the same 779-item catalog, the earlier fit saw 213 items as positives (27.34%) and the expanded fit saw 566 (72.66%).

    What information did the queries contain?

    The earlier training schema allowed the auxiliary analysis field, but it was blank for every training query. The prompt serializer omits blank fields, so the actual training query text for both checkpoints consisted of a summary and description. Both checkpoints also receive those fields in Table 2. The audit therefore gives no evidence that removing populated analysis text disadvantaged the earlier checkpoint relative to its own training inputs.

    In Table 1, the auxiliary field was populated for 16 of 594 queries. A conservative text check for exact item identifiers and unambiguous aliases found that six queries explicitly named at least one relevant item in that field. These are source-text mentions, which may make some queries easier. The field was shared across arms, so the comparison measures all three recipes with that information available. It does not estimate the effect of removing the field, and exact matching can miss indirect clues.

    The frozen Table 2 cohort does not contain the auxiliary field. Matching records in the earlier snapshot provide nonempty text for only six of the 387 queries. That partial archive would not support a matched full-cohort comparison with and without the field.

    Non-neural reference. The native owner-first order uses BM25F+C, query hints and owner routing, with no E5, Laya, Qwen or learned fusion. On the same frozen 594-query, K100 evaluation, Listwise + BCE is +15.83 percentage points higher at Complete@3 and +16.50 at Complete@5. This native baseline does not apply to the separate 387-query experiment.

    Both recipes built around task-specific groups improved Complete@3 by more than six points over the pointwise baseline. At Top-5, grouped BCE gained 6.23 points (paired 95% CI +3.99 to +8.62), and Listwise + BCE gained 6.40 points (+3.90 to +9.17). Their head-to-head difference was 0.17 points (−1.72 to +2.00). The intervals come from 2,000 paired bootstrap draws over duplicate groups.

    The multi-item slice makes that distinction clearer. The pointwise checkpoint recovered all relevant items at Top-5 for 50 of 97 queries (51.55%). Listwise + BCE recovered 52 (53.61%), and grouped BCE recovered 54 (55.67%). Most of the measured gains in the overall comparison came with task-oriented training recipes. The multi-item results show little separation between the two objectives.

    What the other runs taught us

    The expanded checkpoint is the last comparison in this survey. Earlier runs tested different questions: whether an off-the-shelf reranker was enough, whether document adaptation helped before task training, and whether pairwise supervision helped a specialized encoder. Each comparison has its own data and candidate setting. Read the differences within each table.

    How to read the gains

    The experiments support investing in task supervision and more varied training data. In Table 1, both query-grouped recipes improved over the historical pointwise checkpoint, with little separation between the two losses. In Table 2, the checkpoint trained on expanded data improved at both cutoffs under the same composite loss. The two experiments use different cohorts and baselines. Their percentage-point gains cannot rank the value of adding data against changing the objective.

    An earlier sensitivity check found that a separate fusion layer could improve deeper coverage. For the grouped BCE checkpoint, Complete@5 rose from 83.33% to 85.19% with fusion, while Hit@1 fell from 69.02% to 63.47%. The present tables use model scores to compare training recipes and checkpoints. If the decision is which ranking policy to use when Complete@5 matters most, the historical comparison favors keeping fusion as a candidate for evaluation.

    Complete@3 and Complete@5 count a query as complete only when every labeled item appears within the cutoff. A missing gold candidate or a gold set larger than the cutoff makes that impossible. The reference labels are linked to verified catalog identities. They have not been exhaustively adjudicated for each query. The paired intervals describe differences on the observed cohorts and do not account for the selection of experiments reported here.

    A ranking score also has a scale

    The yes/no token margin supplies an ordering. It does not provide a validated probability that an item belongs in the answer. A monotonic transform, such as dividing by a positive temperature, can change the numeric confidence without moving any candidate in the ranking. If the task later becomes choosing how many results to return, it needs a separate calibration dataset and a measure of the costs of missing an item versus suggesting an extra one.[14]

    Decision readout work also gives a way to frame a future comparison. Nokia Applied Research’s AnyJev project explores reading typed decisions from language models. A controlled reranking comparison could keep the backbone and training data fixed, then evaluate the existing token margin against a supervised hidden-state relevance head. That would test what the readout contributes under the same Top-3/5 metrics. Neither the decision-head comparison nor cutoff calibration is part of the reported results.[15]

    For transfer across tasks, a benchmark such as BEIR offers a useful complementary view across retrieval domains. Our tests answer a narrower question about complete recovery for catalog relevance labels. External rankings or leaderboard scores do not establish which model would recover all relevant items in this domain.[16]

    What I would keep from this study

    I would keep Qwen3-Reranker-0.6B fine-tuned on the expanded dataset with listwise cross-entropy and grouped binary cross-entropy as the model-only research reference. It is the checkpoint we evaluated on the expanded data. There is no Grouped BCE checkpoint trained on that dataset. The missing experiment is to train Grouped BCE on the same expanded data, holding the base model, examples, sampling and optimizer schedule fixed, then compare the two objectives on matched candidates. Complete@3 and Complete@5 on multi-item queries would show which recipe better recovers the full set.
